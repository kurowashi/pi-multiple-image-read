# ADR 0003: 返答テキストには、ラベルで識別できない画像だけを載せる

## 状況

初版は、画像の後ろに全件の `位置. パス` を載せていました。根拠は「位置と元パスの対応を確実に渡す」ことでしたが、コストは測っていませんでした。

実測（`chars/4` の概算。日本語の多い入力では実際より少なく見積もります）:

| 入力 | 初版のテキスト | 変更後 |
|---|---|---|
| 1枚 | 約 34 トークン | なし |
| 12枚（短い名前） | 約 134 トークン | なし |
| 48枚（短い名前） | 約 487 トークン | なし |
| 48枚（長い名前、全ラベルが切れる） | 約 1,147 トークン | 約 632 トークン |

画像側は1シートあたり最大約 1,568 トークンです。初版のテキストは全体の 8〜18% を占めていました。
ラベルには既にファイル名が描かれており、一覧の大部分はそれを繰り返していました。

## 決定

テキストブロックは、次のいずれかの画像がある場合だけ返します。

- ラベルが切れた（`label cut off`）
- ラベルが描けなかった（`label not drawn`）
- 同じラベルを持つ別のファイルがある（`label shared with another file`）

一覧は入力の位置番号とパスだけを示します。シートごとの見出し（`Sheet N (positions a-b)`）は削除します。
件数の見出しは、一覧がある場合に限り残します。フォントの注記と小さなタイルの注記は、従来どおり必要なときに出します。

## 理由

- 一覧が必要なのは、ラベルで画像を識別できないときだけです。ラベルが読める画像は、一覧が無くても識別できます。
- 測定で、テキストは最大 18% を占めていました。通常の利用では、その大半が不要な情報です。
- 同名ファイルは、ラベルだけでは区別できないため、一覧に残します。

## 却下した代替

- **全件を列挙（初版）**: 対応は確実ですが、ラベルと重複した情報を毎回払います。
- **テキストなし**: 最も軽いですが、モデルが画像の並びから位置と名前を正しく対応付けられるかを検証していません。切れたラベルや描けなかった文字の画像が出たときに、元のパスを示せなくなります。
- **ディレクトリを1回だけ書き、ファイル名だけを列挙**: 長いパスの削減には効きますが、ラベルと重複する問題は残ります。

## 未検証の点

- モデルが、ラベルの読めた画像だけで正しく識別できるかは、実際のモデルで確認していません（`docs/manual-checks.md` の項目 7）。
- ラベルが切れる条件（12枚のシートで、長い名前の画像が並ぶ場合）が多いと、一覧は全件に近くなります。この場合のコストは初版と同じです。

## 帰結

- 返答テキストの形式を変えたら、この ADR と `test/integration/read-images.test.ts` を同じコミットで更新します。
- 「テキストは常に最後にある」という前提は持ちません。テキストブロックがあれば最後にあることだけを保証します。
